# AI_Prompt

AI Agent 项目级行为约束与编码规范。本文件为永久性约束，适用于项目中所有 AI Agent 会话（包括 Deep Code CLI、Kilo 及其他 AI 工具）。

---

## 核心约束

1. 当用户提出需求时，先分析拆解需求，并将理解列点回馈给用户确认。如果需求极其简单且不存在歧义（例如查询当前时间、简单计算等），可以跳过确认直接执行，但仍需在响应中简要说明你的理解。分析过程中遇到不确定的内容必须及时提问，避免推测性假设。

2. 设计应保持简洁，避免过度设计。执行前需判断设计方案是否会引入不必要的复杂度。若出现以下任一情况，则视为可能过度设计，必须与用户沟通确认后再继续：
    - 新增或修改的文件超过 3 个
    - 引入新的抽象层（如新增基类、中间件、设计模式包装）但无明显复用需求
    - 为单一功能引入第三方库或框架
    - 计划中包含过多未来扩展点（基于当前尚未确认的需求）
      若用户明确要求简洁实现，以上阈值自动降低。

3. 严格控制修改范围，避免修改与当前需求无直接关系的既有代码（即使它们在同一个文件或相邻逻辑块中）。小规模重构（如重命名变量、提取方法）必须事先告知用户，说明原因和影响范围。大规模重构或架构变更必须获得用户明确同意后才能进行。整体开发应遵循已制定的开发规划，避免局部频繁、零散的修改破坏一致性。

4. 当需求包含多步骤操作、存在多种同等合理的技术方案，或需求本身较为模糊时，必须主动列出可选方案及各自的优劣，让用户进行选择确认。禁止在未取得用户确认的情况下直接选择实施路径。

5. 完成代码修改后应及时运行相关测试，验证功能正确性并确认未引入回归问题。测试未通过前不得声称任务完成，必须先排查并修复失败用例。若项目缺少测试框架或测试用例，应主动向用户建议补充，以便后续自动化验证。

6. （元规则）当以上约束彼此冲突，或约束与用户明确指令冲突时，优先级为：用户明确指令 > 安全性/数据完整性 > 本文件中的其他约束。发生冲突时，Agent 必须向用户报告冲突点及采取的仲裁策略。若 Agent 发现自身已违反某条规则，应立即说明并纠正。

## 操作规范

- 会话开始时，检查并设置全局默认编码为 UTF-8（针对命令行工具、脚本文件读写等）。写入任何文件时需显式指定 UTF-8 编码。
- 代码标识符（变量、函数、类名等）使用英文。代码注释使用中文（解释意图、待办事项、复杂逻辑）。文档使用中文，遵循项目既有约定。向用户展示的分析说明文本可用中文。
- 对话及思考中除了专有名词或约定成俗的名词外，其他名称应使用中文。
- 单个文件内容不宜过多。当文件满足以下任一条件时，应考虑拆分为子文件并建立索引，父文件仅保留简述和可跳转的链接：
    - 行数超过 200 行
    - 包含超过 5 个明显可独立描述的功能模块
    - 文件包含多个不同抽象层次的内容（如同时包含高层流程描述和底层实现细节）
- 如果发生计划外操作或与计划产生偏差，必须在操作前向用户说明并寻求确认，同时在日志中记录偏差及原因。
- 每次代码修改完成后，同步更新相关文档（注释、README、API 文档等），确保文档与代码保持一致，不产生过期信息。同步范围包含 `.ai/` 工作区内的计划、日志、笔记等文件，保持工作区记录与实际代码状态一致。
- 如果能够使用版本管理，尽量使用版本管理。具体选择需要根据项目情况给用户提出建议，让用户决定。

## 编码风格

- 使用早返回模式降低嵌套深度，避免超过 3 层嵌套。
- 避免无意义的 `else` —— `if` 块已经 `return` 时直接走后续逻辑。
- 条件/循环体即使只有一行也必须使用大括号。
- 空值检查优先使用早返回或空值合并，避免深层 null 判断嵌套。
- 异步操作优先使用语言的 async/await 模式。
- 优先使用不可变声明（`const`），减少副作用。
- 指针/空值比较使用 `nullptr`（C++），不使用 `NULL` 或 `0`。

## 注释规范

- 类/结构体/枚举：声明处必须有中文注释说明职责和用途。
- 公共方法/属性：必须有中文注释说明功能、参数含义、返回值。
- 重要逻辑分支/生命周期/状态机：必须有一行中文注释解释意图。
- 错误路径：每个错误返回前应有中文注释说明触发条件。
- 关键文件头部需中文注释说明文件职责。

## 约束体系层级

本项目采用三层约束体系：

| 层级 | 文件 | 说明 |
|------|------|------|
| 永久约束 | `AGENTS.md`（本文件） | 核心行为准则 + 编码规范，跨工具通用 |
| 工作区规范 | `AGENTS.md`（本文件，第二部分） | .ai/ 工作区操作流程 |
| 动态规则 | `.ai/dev/dev_core.md` | 项目运行中沉淀的具体规则，`[+]`/`[-]` 开关管理 |

**核心区分原则**：约束体系记录"应该怎么做"；知识库（`.ai/kb/`）记录"这个项目是什么样的"和"遇到问题怎么办"。调试流程、编译流程、架构决策、代码模式 → 写入知识库，不写入本文件。

## .ai/ 工作区操作规范

以下规范描述 `.ai/` 工作区的结构与操作规则。该目录是确保开发一致性的唯一数据源，你必须在每次会话启动时维护其完整性和准确性。

### 会话启动自检

每次会话启动时，必须逐项检查以下目录和文件，缺失则自动创建：

**公共域目录**（如不存在则 `mkdir -p`）：
- `.ai/dev/note/`
- `.ai/log/`
- `.ai/code_review/`
- `.ai/bugs/`
- `.ai/plan/`
- `.ai/kb/`
- `.ai/tmp/`

**公共域文件**（如不存在则创建空文件）：
- `.ai/dev/dev_core.md`
- `.ai/dev/current.md`
- `.ai/kb/index.md`

**私域目录**（基于 `.ai/.info.json` 获取的 `{username}`）：
- `.ai/users/{username}/log/`
- `.ai/users/{username}/note/`
- `.ai/users/{username}/code_review/`
- `.ai/users/{username}/bugs/`
- `.ai/users/{username}/tmp/`

**私域文件**：
- `.ai/users/{username}/dev_last.md`

### 公域与私域

.ai 目录分为**公共域**与**私域**两部分：
- **公共域**：`.ai/dev/`、`.ai/log/`、`.ai/code_review/`、`.ai/bugs/`、`.ai/plan/`、`.ai/kb/`、`.ai/tmp/` — 项目级共享，纳入 Git
- **私域**：`.ai/users/{username}/` — 个人操作状态、日志、笔记、代码审查、Bug 追踪，加入 `.gitignore` 不纳入版本管理

所有用户（含单人项目）均遵循此分区结构。

### 用户身份

读取 `.ai/.info.json` 获取当前用户名。若文件不存在或 `user` 为空，则执行 `git config user.name` 获取 Git 用户名并写入。若无 Git 配置则选取默认用户名。

**路径自校验**：访问 `.ai/users/{username}/` 下文件时，若返回 "file not found"，先执行 `read .ai/.info.json` 重新获取正确的 `username` 并修正路径后重试。连续失败则向用户报告。

### 开发目录

> `.ai/dev/`

- **`dev_core.md`**：长期有效规则。每条规则前带 `[+]`（启用）/ `[-]`（禁用），只能标记禁用不能删除，禁用超 10 条时提醒用户清理。
- **`current.md`**：记录当前正在进行的工作，按 `@{username} 描述正在进行的工作` 范式维护各成员进度。
- **`note/dev_note.md`**：团队共享开发笔记。

### 日志

> `.ai/log`

**公共日志**仅记录团队级重要事件（公共域文件修改、里程碑达成、high 优先级审查/Bug、跨成员关键操作）。日常操作记录在私域日志 `.ai/users/{username}/log/`。

日志按年/月/日分层归档，文件命名 `yyyy-mm-dd-{username}-NNN.md`。日目录含 `day_index.md`。根目录维护 `index.md` 和 `log.md`（最近 30 条摘要）。

### 计划

> `.ai/plan`

当用户提出涉及多步骤、跨会话、多模块的任务时，主动在 `plan.md` 中创建对应条目。

计划分两层：
- **大计划**（`plan.md`）：整体目标、技术架构、核心里程碑
- **小计划**（`{stage}/` 子目录）：具体任务分解与实施步骤

`plan_index.md` 存放各期计划索引。`plan_log.md` 记录变更摘要。发生计划外操作必须先向用户说明。

#### 子计划状态

每个小计划阶段目录下维护 `status.md`：

```markdown
# {stage} 状态

- **执行模式**：manual | auto
- **自动推进**：disabled | enabled
- **状态**：planned | ready_for_code | coding | ready_for_review | review_failed | review_passed | ready_for_test | test_writing | testing | bug_found | bug_fixing | done | paused
- **当前责任人**：ai | user
- **更新时间**：yyyy-mm-dd HH:MM

## 当前任务
...

## 阻塞 / 暂停原因
...

## 状态记录
| 时间 | 状态变化 | 说明 |
|------|----------|------|
```

状态含义：
- `planned`：计划已创建，等待确认
- `ready_for_code`：可进入编码实现
- `coding`：正在编码实现
- `ready_for_review`：实现完成，等待审查
- `review_failed`：审查不通过，需修改
- `review_passed`：审查通过
- `ready_for_test`：等待测试编写或验收
- `test_writing`：正在编写测试
- `testing`：正在执行测试验收
- `bug_found`：测试发现缺陷
- `bug_fixing`：正在修复缺陷
- `done`：完成
- `paused`：暂停，需用户决策

**默认模式**：`执行模式=manual`，`自动推进=disabled`。仅在用户明确开启时改为 `auto` + `enabled`。暂停条件：计划外架构变更、修改范围超出计划、测试环境缺失、连续两次验收失败。

### 知识库

> `.ai/kb/`

```
.ai/kb/
├── index.md           # 总索引
├── architecture.md    # 架构决策、设计理由、技术选型
├── patterns.md        # 代码模式、项目约定、最佳实践
├── troubleshooting.md # 常见问题、调试流程、已知坑位
└── setup.md           # 环境搭建、构建流程、依赖管理
```

写入规范：

| 类型 | 写入路径 |
|------|----------|
| 架构决策 | `architecture.md` |
| 代码模式 | `patterns.md` |
| 排查经验 | `troubleshooting.md` |
| 环境配置 | `setup.md` |

禁止写入知识库：行为约束（→ AGENTS.md）、工作区维护规则（→ dev_core.md）。每次写入后在公共日志中记录。

### 代码审查

> `.ai/users/{username}/code_review/`

管理开发阶段的代码评审问题，按计划阶段组织。审查问题集中在 `REV-{plan_stage}.md`。

条目模板：

```markdown
## REV-{NO}: {简要标题}
- **状态**：pending | fixing | resolved | closed
- **优先级**：high | medium | low
- **提出时间**：yyyy-mm-dd HH:MM

### 问题描述
...

### 处理记录
| 时间 | 操作者 | 说明 | Commit |
|------|--------|------|--------|

### 验收记录
| 时间 | 验收人 | 结论 | 备注 |
|------|--------|------|------|
```

根目录维护 `index.md`（按阶段分组索引）和 `log.md`（最近 30 条变更摘要）。`pending` 且 `high` 优先级的问题须写入公共日志。

### Bug 追踪

> `.ai/users/{username}/bugs/`

管理测试阶段发现的缺陷，按模块组织：

```
.ai/users/{username}/bugs/
├── index.md              # 按模块分组索引
├── log.md                # 最近 30 条变更摘要
├── {module_a}/
│   ├── BUG-001_标题.md
│   └── BUG-002_标题.md
└── {module_b}/
    └── BUG-001_标题.md
```

Bug 模板：

```markdown
# BUG-{NNN}: {简要标题}

- **状态**：open | fixing | resolved | closed
- **模块**：{模块名}
- **优先级**：high | medium | low

## 描述
...

## 复现步骤
1. ...

## 期望行为
...

## 实际行为
...

## 修复记录
| 时间 | 操作者 | 说明 | Commit |
|------|--------|------|--------|

## 验收记录
| 时间 | 验收人 | 结论 | 备注 |
|------|--------|------|------|
```

### 审查/追踪生命周期

```
pending/open  ──→  fixing  ──→  resolved  ──→  closed
      ↑                         │
      └────────── 验收不通过 ───┘
```

| 状态 | 代码审查 | Bug 追踪 |
|------|---------|---------|
| 起始 | `pending` | `open` |
| 修复中 | `fixing` | `fixing` |
| 待验收 | `resolved` | `resolved` |
| 关闭 | `closed` | `closed` |

## Skill 系统

本项目提供了 5 个 Skill（AI 能力模块），通过 `/` 菜单或自动匹配调用：

| Skill | 用途 |
|-------|------|
| `check-kb` | 查阅 `.ai/kb/` 知识库 |
| `get-bugs` | 获取当前模块待处理 Bug |
| `bug-acceptance` | 标准化 Bug 验收流程 |
| `get-stage-status` | 读取子计划状态 |
| `update-stage-status` | 更新子计划状态 |

在 Deep Code CLI 中使用 `/skills` 查看完整列表，或 `/` 菜单选择调用。
